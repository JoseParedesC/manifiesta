# 03. Arquitectura de solución

**Estado:** Aprobada  
**Versión:** 0.1

## 3.1. Estilo arquitectónico

La solución utilizará una arquitectura **Modular Monolith**, complementada con principios de Clean Architecture y DDD pragmático.

El sistema se desplegará inicialmente como una aplicación backend única, organizada internamente en módulos funcionales con responsabilidades delimitadas.

### Principios

- Separación de responsabilidades.
- Alta cohesión dentro de cada módulo.
- Bajo acoplamiento entre módulos.
- Reutilización de componentes y lógica.
- Independencia de las reglas de negocio frente a tecnologías externas.
- Trazabilidad de operaciones.
- Aislamiento de datos entre empresas.
- Preparación para escalabilidad horizontal.

No se implementarán microservicios en la primera versión.

La modularidad deberá permitir evolucionar funcionalidades sin necesidad de dividir prematuramente la aplicación en servicios independientes.

### Responsabilidades de las capas

**Domain**
- Entidades y agregados.
- Objetos de valor.
- Reglas e invariantes de negocio.
- Eventos de dominio.
- Contratos propios del dominio cuando sean necesarios.

**Application**
- Casos de uso.
- Commands y Queries.
- Handlers.
- Validaciones.
- Coordinación de operaciones.
- Contratos para servicios externos.
- Motores de procesamiento cuando su responsabilidad corresponda a la aplicación.

**Infrastructure**
- Implementaciones de persistencia.
- Integraciones externas.
- Servicios técnicos.
- Acceso a almacenamiento de objetos.
- Implementaciones de servicios definidos mediante contratos.

**API**
- Exposición de endpoints REST.
- Autenticación y autorización HTTP.
- Recepción y validación de solicitudes.
- Despacho de Commands y Queries.
- Transformación de resultados en respuestas HTTP.

Los módulos serán propietarios de sus entidades y reglas. Otros módulos deberán interactuar mediante contratos públicos, no mediante el acceso indiscriminado a sus implementaciones internas.

## 3.4. Autenticación y gestión de usuarios

Se implementará autenticación híbrida.

### Proveedores

- ASP.NET Core Identity para usuarios y contraseñas locales.
- Google OAuth / OpenID Connect para autenticación externa.
- JWT para autorización de solicitudes a la API.

Las contraseñas locales se almacenarán mediante mecanismos seguros de hashing. Nunca se almacenarán en texto plano.

Las cuentas de Google podrán vincularse con cuentas locales existentes.

Google será un proveedor de identidad, no el administrador de permisos funcionales del ERP.

### Identidad global y membresías

Un usuario tendrá una identidad global y podrá pertenecer a varias empresas.

Se diferenciarán:

- Identidad y credenciales del usuario.
- Empresa o tenant.
- Membresía del usuario dentro de una empresa.
- Roles y permisos dentro de cada empresa.

El usuario podrá cambiar de empresa activa sin necesitar cuentas independientes.

Identity será responsable de las credenciales e identidad; Tenants administrará empresas, membresías y aspectos relacionados con los planes y cupos.

### Control de cupos

Se utilizará el modelo de membresías habilitadas:

- Cada membresía activa consume un cupo dentro de su empresa.
- Un mismo usuario puede consumir cupos en distintas empresas.
- Las membresías deshabilitadas no consumen cupos.
- Los cupos se verificarán al invitar o activar usuarios.
- Las operaciones de asignación de cupos deberán protegerse frente a concurrencia.

### Sesiones

Se permitirá una única sesión autenticada activa por identidad global.

Si un usuario inicia sesión desde otro dispositivo:

1. Se crea la nueva sesión.
2. Se invalida la sesión anterior.
3. El dispositivo anterior deberá autenticarse nuevamente.

Las sesiones y los refresh tokens serán persistidos en PostgreSQL, con capacidad de revocación.

Los JWT de acceso tendrán duración limitada. El backend validará que la sesión asociada siga vigente para hacer efectiva la revocación.

## 3.5. CQRS y Mediator

Se implementará CQRS para separar las operaciones de lectura y escritura.

Se utilizará la biblioteca **Mediator**, desarrollada por Martin Othamar.

Repositorio oficial: https://github.com/martinothamar/Mediator

Se utilizará para:

- Despachar Commands.
- Despachar Queries.
- Resolver sus respectivos Handlers.
- Incorporar comportamientos transversales mediante pipeline behaviors.
- Centralizar validaciones y otras operaciones comunes cuando corresponda.

La implementación no dependerá de MediatR.

CQRS no implica utilizar bases de datos independientes para lectura y escritura. Inicialmente ambas operaciones utilizarán PostgreSQL y Entity Framework Core.

El dominio no tendrá dependencia directa de Mediator.

## 3.6. Comunicación entre módulos

Se utilizará un modelo híbrido de comunicación.

### Comunicación síncrona

Mediante contratos públicos e interfaces cuando un módulo necesite solicitar información o ejecutar una operación y requiera una respuesta inmediata.

### Comunicación mediante eventos

Los eventos internos permitirán notificar hechos ocurridos para que otros módulos ejecuten procesos secundarios.

Ejemplos:

- Un servicio de transporte finalizado.
- Una factura registrada.
- Un pago aplicado.
- Una liquidación cerrada.

Los eventos deberán diseñarse para soportar idempotencia cuando puedan generar efectos financieros.

Se evaluará el patrón Outbox cuando se requiera garantizar la publicación confiable de eventos asociados a transacciones persistidas.

Inicialmente no se incorporará RabbitMQ ni otro broker externo.

Los eventos en proceso no reemplazarán las transacciones que requieran integridad financiera.

## 3.7. Persistencia y acceso a datos

Se utilizará un único `ApplicationDbContext` compartido por toda la solución.

No se implementará un DbContext independiente por módulo en la primera versión.

### Organización

- Configuraciones mediante `IEntityTypeConfiguration<TEntity>`.
- Configuraciones de entidades organizadas por módulo.
- Migraciones centralizadas.
- Acceso mediante Entity Framework Core.
- PostgreSQL como motor de persistencia.

Aunque el DbContext sea compartido, cada módulo conservará la propiedad conceptual de sus entidades.

El acceso cruzado a entidades no será libre: se mantendrán los contratos y límites de cada módulo.

## 3.8. Estrategia multi-tenant

Se utilizará una arquitectura de base de datos compartida y tablas compartidas con columna `TenantId`.

### Reglas

- Las entidades que pertenezcan a una empresa tendrán `TenantId`.
- El backend determinará el tenant a partir de la identidad autenticada y la membresía seleccionada.
- No se confiará en un `TenantId` enviado libremente por el frontend.
- Se implementarán Global Query Filters en EF Core.
- Las operaciones de escritura tendrán validaciones explícitas de pertenencia al tenant.
- Las relaciones y consultas sensibles deberán comprobar el aislamiento.
- Los índices y restricciones únicas deberán incluir `TenantId` cuando corresponda.
- Cualquier operación que omita filtros globales requerirá autorización y validación explícita.

Se incorporarán pruebas de integración para verificar que una empresa no pueda consultar ni modificar información perteneciente a otra.

No se implementará Row-Level Security de PostgreSQL en la primera versión.

## 3.9. Motores de procesamiento backend

Se implementará una arquitectura híbrida compuesta por un motor central de despacho y motores especializados por dominio.

### 3.9.1. Motor central de solicitudes

Su responsabilidad será recibir solicitudes de procesamiento, identificar su tipo y derivarlas al Handler correspondiente.

El mecanismo se apoyará en Mediator.

Flujo conceptual:

```text
Solicitud HTTP
      |
      v
API REST
      |
      v
Validación y autorización
      |
      v
Mediator / Dispatcher
      |
      v
Command o Query Handler
      |
      v
Procesamiento correspondiente
      |
      v
Respuesta estructurada
      |
      v
Respuesta HTTP
```

El motor central no contendrá las reglas de negocio particulares de cada módulo.

### 3.9.2. Motores especializados

Serán componentes responsables de ejecutar procesos, cálculos y reglas de negocio reutilizables.

Motores previstos inicialmente:

| Motor | Responsabilidad |
|---|---|
| Motor de liquidaciones | Cálculos y reglas para liquidaciones de vehículos y conductores. |
| Motor de rentabilidad | Determinación de resultados económicos por vehículo y periodo. |
| Motor financiero | Procesamiento de operaciones financieras y sus reglas. |
| Motor de facturación | Cálculos, validaciones y procesamiento de documentos de facturación. |
| Motor de distribución | Aplicación de acuerdos y reglas de distribución de utilidades. |

La lista es inicial y podrá evolucionar según las necesidades funcionales.

### 3.9.3. Contratos de procesamiento

Los motores especializados deberán:

- Recibir solicitudes mediante contratos definidos.
- Validar las entradas que correspondan a su responsabilidad.
- Ejecutar las reglas de negocio.
- Devolver respuestas estructuradas.
- Ser independientes de los controladores HTTP.
- Poder probarse de manera aislada.
- Evitar duplicación de reglas entre módulos.

Los Handlers coordinarán los casos de uso y utilizarán los motores correspondientes.

No se permitirá que un único motor genérico concentre todas las reglas del ERP.

## 3.10. API REST

Se expondrá una única API REST mediante ASP.NET Core Web API.

### Convenciones

- Comunicación HTTP/HTTPS.
- Intercambio de información JSON.
- Versionamiento inicial mediante `/api/v1/`.
- Endpoints organizados por recursos y módulos.
- OpenAPI/Swagger para documentación.
- Códigos HTTP semánticos.
- Validación de solicitudes.
- Autenticación mediante JWT.
- Despacho de Commands y Queries mediante Mediator.

Ejemplo:

```text
GET    /api/v1/vehicles
GET    /api/v1/vehicles/{id}
POST   /api/v1/vehicles
PUT    /api/v1/vehicles/{id}
DELETE /api/v1/vehicles/{id}
```

La API no contendrá directamente reglas complejas de negocio.

## 3.11. Arquitectura frontend

Se utilizará React + TypeScript + Vite.

La organización será modular por funcionalidades (*Feature-Based Architecture*).

Cada funcionalidad tendrá sus propias páginas, componentes, hooks, servicios y tipos cuando corresponda.

### Tecnologías

| Responsabilidad | Tecnología |
|---|---|
| Interfaz | React |
| Lenguaje | TypeScript |
| Bundler | Vite |
| Navegación | React Router |
| Estado del servidor | TanStack Query |
| Estado global | Zustand |
| Formularios | React Hook Form |
| Validación | Zod |
| Comunicación API | Cliente HTTP centralizado |

### Reutilización

Se mantendrá una biblioteca compartida de componentes reutilizables.

También se centralizarán:

- Hooks comunes.
- Servicios de acceso a la API.
- Utilidades.
- Tipos y contratos compartidos cuando corresponda.
- Componentes de formularios.
- Validaciones reutilizables.
- Manejo de errores.
- Elementos de interfaz comunes.

Se evitará duplicar componentes o lógica entre funcionalidades.

La reutilización no deberá generar dependencias innecesarias entre módulos funcionales.

## 3.12. Gestión de estado frontend

Se utilizará una combinación de TanStack Query, Zustand y React Context.

| Tecnología | Responsabilidad |
|---|---|
| TanStack Query | Datos del servidor, caché, consultas, mutaciones y sincronización con API. |
| Zustand | Estado global del cliente, empresa activa y preferencias de interfaz. |
| React Context | Estado compartido de alcance limitado. |
| React Hook Form | Estado y gestión de formularios. |

### Reglas

- No duplicar en Zustand información administrada por TanStack Query.
- Centralizar las solicitudes HTTP.
- Mantener separado el estado del servidor del estado de interfaz.
- Los permisos se validarán definitivamente en backend.
- El cambio de empresa activa deberá actualizar el contexto de las consultas.
- Se evitará mostrar información almacenada en caché correspondiente a otra empresa.

## 3.13. Almacenamiento de archivos

Se utilizará almacenamiento de objetos compatible con S3.

Los archivos no se almacenarán directamente en PostgreSQL ni dependerán del disco local del backend.

PostgreSQL conservará los metadatos y referencias de los archivos.

### Características

- Archivos privados.
- Autorización de cargas y descargas desde backend.
- URLs firmadas temporales cuando corresponda.
- Validación de tamaño.
- Validación de extensión.
- Validación de tipo MIME.
- Separación lógica por tenant.

Ejemplo de organización:

```text
tenant/{tenantId}/
├── invoices/
├── manifests/
├── expenses/
├── payments/
└── advances/
```

La separación por prefijos no reemplaza las validaciones de autorización del backend.

El proveedor específico se seleccionará posteriormente, evaluando disponibilidad, costos e integración con Railway.

## 3.14. Despliegue e infraestructura

La infraestructura inicial utilizará Docker y Railway.

### Componentes

- Un servicio backend ASP.NET Core.
- Un frontend independiente.
- Un servicio PostgreSQL.
- Un proveedor de almacenamiento de objetos externo.

### Reglas de despliegue

- Dockerfile explícito para el backend.
- Configuración de variables de entorno y secretos.
- Migraciones ejecutadas como proceso controlado e independiente.
- No ejecutar migraciones automáticamente en cada arranque de una réplica.
- Preparación para escalar horizontalmente el backend mediante réplicas.

La arquitectura no requerirá Redis, RabbitMQ, Kubernetes ni microservicios inicialmente.

El aumento de réplicas del backend no implica crear servicios independientes por módulo.

## 3.15. Estrategia de pruebas

Se adoptará una estrategia progresiva.

La incorporación de niveles adicionales de pruebas dependerá de una decisión explícita del responsable del proyecto.

### Niveles previstos

| Nivel | Propósito |
|---|---|
| Unitarias | Verificar reglas de negocio, cálculos, motores y validaciones. |
| Integración | Verificar persistencia, EF Core, PostgreSQL, API y comunicación entre módulos. |
| Arquitectura | Verificar dependencias, límites modulares y convenciones. |
| E2E | Verificar flujos completos desde frontend hasta backend. |

### Implementación inicial

Se comenzará con:

- Pruebas unitarias.
- Pruebas de integración.

Posteriormente podrán incorporarse pruebas de arquitectura y E2E.

No se establecerán porcentajes mínimos obligatorios de cobertura inicialmente.

El incremento de rigurosidad, cobertura, herramientas y complejidad deberá ser aprobado por el responsable del proyecto.

## 3.16. Principios y restricciones arquitectónicas

La solución deberá respetar los siguientes principios:

1. Mantener un backend único y modular.
2. Evitar introducir microservicios prematuramente.
3. Mantener límites claros entre módulos.
4. Reutilizar componentes y lógica sin crear dependencias innecesarias.
5. Centralizar el despacho de solicitudes.
6. Separar la coordinación de casos de uso de las reglas de negocio.
7. Mantener los motores especializados independientes de HTTP.
8. Garantizar el aislamiento multi-tenant desde backend.
9. Preservar la integridad de las operaciones financieras.
10. Evitar duplicación de datos y cálculos.
11. Mantener las decisiones tecnológicas sujetas a evaluación y aprobación.
12. Incorporar complejidad arquitectónica y de pruebas de forma progresiva.

## 3.17. Decisiones diferidas

Los siguientes elementos no forman parte de las decisiones cerradas de esta sección:

- Proveedor específico de almacenamiento de objetos.
- Incorporación de Redis.
- Incorporación de RabbitMQ u otro broker.
- Implementación de microservicios.
- Implementación de PostgreSQL Row-Level Security.
- Estrategia avanzada de observabilidad.
- Políticas obligatorias de cobertura de pruebas.
- Infraestructura avanzada de CI/CD.

Estas decisiones se evaluarán cuando exista una necesidad funcional, técnica u operativa que las justifique.
