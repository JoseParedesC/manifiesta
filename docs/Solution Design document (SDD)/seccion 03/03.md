# 03. Arquitectura de solución

## 3.1. Objetivo

Definir la arquitectura técnica y las decisiones estructurales que orientarán el desarrollo del sistema SaaS de gestión administrativa, operativa y financiera para empresas de transporte de carga.

La arquitectura deberá proporcionar:

- Separación clara de responsabilidades.
- Modularidad funcional y técnica.
- Aislamiento de información entre empresas.
- Reutilización de componentes, servicios y reglas de negocio.
- Facilidad de mantenimiento y evolución.
- Integridad de la información financiera y operativa.
- Capacidad de escalar progresivamente.
- Independencia razonable entre los módulos funcionales.
- Facilidad para implementar, probar y desplegar nuevas funcionalidades.

La solución se implementará inicialmente como un monolito modular, evitando la complejidad operativa de una arquitectura distribuida sin renunciar a una organización interna que permita evolucionar posteriormente.

## 3.2. Arquitectura general

Se adopta una arquitectura:

**Modular Monolith + Clean Architecture + DDD pragmático.**

El sistema tendrá un único backend centralizado, organizado internamente por módulos funcionales independientes.

La solución estará compuesta por:

1. Backend centralizado en ASP.NET Core.
2. Frontend independiente desarrollado con React y TypeScript.
3. Base de datos PostgreSQL compartida.
4. Almacenamiento de objetos mediante Railway Storage Buckets.
5. Infraestructura de despliegue basada en Docker y Railway.

### 3.2.1. Modular Monolith

El backend será una única aplicación ASP.NET Core que contendrá todos los módulos funcionales.

Cada módulo tendrá responsabilidades delimitadas y una organización interna propia.

No se implementarán microservicios inicialmente.

La modularidad deberá permitir:

- Mantener responsabilidades separadas.
- Evitar dependencias innecesarias entre módulos.
- Reutilizar componentes y servicios compartidos.
- Facilitar pruebas independientes.
- Evolucionar módulos sin afectar innecesariamente a los demás.

La separación modular será principalmente lógica y organizacional, no una separación física de servicios o bases de datos.

### 3.2.2. Clean Architecture

Se aplicará Clean Architecture para separar las responsabilidades del dominio, los casos de uso y los mecanismos de infraestructura.

Las capas principales serán:

- **Domain:** entidades, objetos de valor, reglas e invariantes del dominio.
- **Application:** casos de uso, Commands, Queries, handlers, contratos y coordinación de procesos.
- **Infrastructure:** persistencia, proveedores externos, almacenamiento y servicios técnicos.
- **API:** exposición de endpoints HTTP, autenticación, autorización y composición de dependencias.

Las dependencias deberán dirigirse hacia el dominio y los contratos internos, evitando que las reglas de negocio dependan de detalles de infraestructura.

### 3.2.3. DDD pragmático

Se aplicarán principios de Domain-Driven Design cuando aporten claridad y consistencia al modelo de negocio.

Se utilizarán:

- Entidades y objetos de valor.
- Agregados cuando sean necesarios para proteger invariantes.
- Servicios de dominio.
- Repositorios cuando aporten valor real.
- Eventos de dominio.
- Límites funcionales entre módulos.

No se introducirán abstracciones o patrones innecesarios únicamente por seguir una metodología.

## 3.4. Backend

### 3.4.1. Tecnología

| Componente | Tecnología |
|---|---|
| Lenguaje | C# |
| Framework | ASP.NET Core |
| ORM | Entity Framework Core |
| Base de datos | PostgreSQL |
| Arquitectura | Modular Monolith + Clean Architecture |
| Mediador | Mediator de Martin Othamar |
| API | REST |
| Documentación API | OpenAPI / Swagger |

### 3.4.2. CQRS

Se implementará CQRS (*Command Query Responsibility Segregation*) para separar las operaciones que modifican información de las operaciones que consultan información.

Se utilizarán:

- Commands para operaciones de escritura.
- Queries para operaciones de lectura.
- Handlers para ejecutar los casos de uso.
- Validaciones mediante mecanismos compartidos.
- Pipeline behaviors para responsabilidades transversales.

CQRS será una separación lógica dentro del mismo backend y utilizará la misma base de datos PostgreSQL.

No se implementará una base de datos independiente para lecturas y escrituras.

### 3.4.3. Biblioteca Mediator

Se utilizará la biblioteca **Mediator**, desarrollada por Martin Othamar.

Repositorio oficial:

https://github.com/martinothamar/Mediator

No se utilizará MediatR.

Mediator permitirá:

- Despachar Commands y Queries.
- Resolver sus respectivos handlers.
- Implementar comportamientos transversales.
- Aprovechar generación de código en tiempo de compilación.
- Reducir dependencias y mecanismos de reflexión en tiempo de ejecución.

La biblioteca se utilizará en las capas Application y API, sin introducir dependencias innecesarias en el dominio.

### 3.4.4. Motores de procesamiento

La arquitectura tendrá dos niveles complementarios de procesamiento.

**Nivel central: Dispatcher / Mediator**

Recibe Commands y Queries, identifica el handler correspondiente y coordina la ejecución del caso de uso.

**Nivel especializado: motores de dominio y procesos**

Implementará motores reutilizables para procesos que concentren reglas y cálculos especializados.

Ejemplos:

- Motor de liquidaciones.
- Motor de rentabilidad.
- Motor de procesos financieros.
- Motor de facturación.
- Motor de distribución de utilidades.

Estos motores:

- Recibirán solicitudes mediante contratos definidos.
- Ejecutarán reglas y cálculos especializados.
- Devolverán resultados estructurados.
- Serán independientes de HTTP y de los controladores.
- Podrán probarse de forma aislada.
- Evitarán concentrar toda la lógica en los handlers.

No se creará un motor genérico que concentre responsabilidades de todos los procesos.

Los motores son mecanismos internos de implementación, no módulos funcionales adicionales.

### 3.4.5. Reutilización

La solución deberá evitar duplicación innecesaria de lógica.

Se priorizará la reutilización de:

- Servicios compartidos.
- Validaciones.
- Reglas de negocio.
- Componentes de infraestructura.
- Motores de procesamiento.
- Contratos de comunicación.
- Utilidades técnicas.

La reutilización deberá mantener responsabilidades claras y evitar dependencias circulares o abstracciones excesivamente genéricas.

## 3.5. Comunicación entre módulos

Se utilizará un modelo híbrido de comunicación.

### 3.5.1. Comunicación directa

Se utilizará cuando un módulo necesite una respuesta inmediata de otro módulo para completar un caso de uso.

Se realizará mediante contratos públicos e interfaces.

No se permitirá acceder directamente a clases o implementaciones internas de otros módulos.

### 3.5.2. Eventos internos

Se utilizarán eventos para comunicar hechos ocurridos y notificar procesos secundarios.

Ejemplos:

- Creación de un servicio.
- Registro de una factura.
- Aplicación de un pago.
- Cierre de una liquidación.
- Actualización de información que afecte reportes.

Inicialmente los eventos serán procesados dentro del mismo proceso del backend.

No se incorporará RabbitMQ ni otro broker externo en la primera versión.

Los eventos financieros deberán diseñarse considerando idempotencia y consistencia.

Cuando sea necesario garantizar la publicación confiable de eventos asociados a transacciones, se evaluará el patrón Outbox.

Los eventos no sustituirán transacciones cuando se requiera garantizar integridad financiera.

## 3.6. Persistencia y acceso a datos

### 3.6.1. Base de datos

Se utilizará PostgreSQL como motor de persistencia.

La base de datos será compartida entre todos los módulos y empresas.

No se crearán bases de datos independientes por módulo ni por empresa en la primera versión.

### 3.6.2. ApplicationDbContext compartido

Se utilizará un único `ApplicationDbContext` compartido para toda la solución.

Las entidades estarán organizadas por módulo, pero serán gestionadas por el mismo contexto de EF Core.

Las configuraciones se organizarán mediante implementaciones de:

`IEntityTypeConfiguration<TEntity>`

Cada módulo será responsable de definir las configuraciones correspondientes a sus entidades.

Las migraciones serán centralizadas.

La existencia de un contexto compartido no significa que los módulos puedan manipular libremente entidades pertenecientes a otros módulos.

### 3.6.3. Consideraciones de persistencia

- Las relaciones deberán respetar los límites del dominio.
- Las operaciones financieras deberán utilizar tipos decimales.
- En C# se utilizará `decimal`.
- En PostgreSQL se utilizará `NUMERIC`.
- Las restricciones únicas deberán considerar `TenantId` cuando corresponda.
- Las operaciones que involucren varias entidades deberán respetar las transacciones necesarias.
- Las consultas deberán optimizarse según sus necesidades de lectura.

## 3.7. Arquitectura multi-tenant

Se implementará un modelo de base de datos compartida con tablas compartidas y separación lógica mediante `TenantId`.

### 3.7.1. Modelo seleccionado

- Una única base de datos PostgreSQL.
- Tablas compartidas entre empresas.
- Entidades empresariales asociadas a un `TenantId`.
- Índices y restricciones que contemplen el tenant.
- Contexto empresarial resuelto por el backend.

### 3.7.2. Resolución del tenant

El backend determinará la empresa activa a partir de la identidad autenticada y la membresía correspondiente.

Nunca se confiará exclusivamente en un `TenantId` enviado por el frontend.

En cada solicitud empresarial se deberá validar:

1. Identidad autenticada.
2. Empresa activa.
3. Membresía del usuario.
4. Estado de la membresía.
5. Autorización correspondiente.
6. Propiedad y pertenencia de los registros consultados o modificados.

### 3.7.3. Global Query Filters

Se utilizarán filtros globales de EF Core mediante `HasQueryFilter` para aplicar automáticamente el aislamiento por tenant.

También se realizarán validaciones explícitas en:

- Escrituras.
- Relaciones entre entidades.
- Consultas sensibles.
- Operaciones que involucren varias empresas.
- Procesos que requieran omitir filtros.

Las operaciones que omitan filtros globales deberán estar protegidas mediante autorización y validaciones explícitas.

### 3.7.4. Restricciones adicionales

- No se implementará Row-Level Security de PostgreSQL en la primera versión.
- Las consultas deberán evitar accesos cruzados entre empresas.
- Los índices y claves únicas deberán considerar el tenant.
- Se realizarán pruebas de integración para verificar el aislamiento.

## 3.8. Autenticación y sesiones

### 3.8.1. Autenticación híbrida

Se utilizará ASP.NET Core Identity para gestionar usuarios y credenciales locales.

También se permitirá autenticación mediante Google OAuth / OpenID Connect.

Características:

- Usuarios globales.
- Credenciales locales almacenadas mediante hashing seguro.
- Vinculación de cuentas Google con usuarios existentes.
- Identidad independiente de las membresías empresariales.
- Roles y permisos administrados internamente por el ERP.
- JWT para autorización de la API.

Google será un proveedor de identidad, no el responsable de administrar roles ni permisos del ERP.

### 3.8.2. Gestión de sesiones

Se mantendrá una sola sesión autenticada activa por identidad global en toda la plataforma.

Cuando un usuario inicie sesión en otro dispositivo:

- La nueva sesión reemplazará la anterior.
- La sesión anterior quedará invalidada.
- El dispositivo anterior deberá volver a autenticarse.

Las sesiones se persistirán en PostgreSQL.

Se utilizarán identificadores de sesión y refresh tokens revocables.

Los JWT de acceso tendrán una duración corta.

El backend deberá validar la vigencia de la sesión para que la revocación sea efectiva. No se dependerá exclusivamente de JWT stateless.

El contexto de empresa activa y la membresía correspondiente deberán validarse en cada solicitud empresarial.

## 3.9. API

Se utilizará una API REST centralizada en ASP.NET Core.

Características:

- Comunicación HTTP/HTTPS.
- Formato JSON.
- Versionamiento de rutas.
- Documentación OpenAPI / Swagger.
- Códigos HTTP semánticos.
- Validación centralizada de solicitudes.
- Autenticación mediante JWT.
- Autorización mediante políticas y permisos.
- Despacho de Commands y Queries mediante Mediator.

Convención inicial:

`/api/v1/{modulo}/{recurso}`

Ejemplos:

```http
GET    /api/v1/vehicles
POST   /api/v1/vehicles
GET    /api/v1/vehicles/{id}
PUT    /api/v1/vehicles/{id}
DELETE /api/v1/vehicles/{id}
```

Los endpoints deberán limitarse a recibir solicitudes, validar aspectos de entrada y delegar la ejecución a los casos de uso correspondientes.

No deberán concentrar reglas de negocio.

## 3.10. Frontend

### 3.10.1. Tecnología

| Componente | Tecnología |
|---|---|
| Framework | React |
| Lenguaje | TypeScript |
| Herramienta de construcción | Vite |
| Enrutamiento | React Router |
| Estado del servidor | TanStack Query |
| Estado global cliente | Zustand |
| Formularios | React Hook Form |
| Validación | Zod |

### 3.10.2. Arquitectura modular

El frontend tendrá una arquitectura Feature-Based organizada por módulos funcionales.

Cada módulo podrá contener:

- Páginas.
- Componentes.
- Hooks.
- Servicios.
- Tipos.
- Esquemas de validación.

Se mantendrá una biblioteca de componentes compartidos para evitar duplicaciones y conservar consistencia visual y funcional.

### 3.10.3. Cliente HTTP

Se implementará un cliente HTTP centralizado responsable de:

- Comunicación con la API.
- Inclusión de credenciales y contexto de autenticación.
- Tratamiento de errores.
- Normalización de respuestas.
- Manejo de respuestas de autorización.
- Reutilización de configuraciones de comunicación.

Los componentes y módulos no deberán implementar clientes HTTP independientes sin una justificación técnica.

### 3.10.4. Gestión del estado

Se utilizarán mecanismos diferenciados según el tipo de información.

**TanStack Query**

Responsable de datos del servidor, caché, consultas y mutaciones.

**Zustand**

Responsable de estado global del cliente, como empresa activa y preferencias de interfaz.

**React Context**

Para estados compartidos de alcance limitado.

**React Hook Form**

Para el estado y gestión de formularios.

No se duplicarán en Zustand datos que ya estén administrados por TanStack Query.

Cuando cambie la empresa activa, deberán actualizarse las consultas y evitarse datos almacenados en caché que pertenezcan a la empresa anterior.

La autorización definitiva siempre corresponderá al backend.

## 3.11. Almacenamiento de archivos

### 3.11.1. Proveedor aprobado

Se utilizará **Railway Storage Buckets** como proveedor inicial de almacenamiento de objetos.

Los buckets ofrecen compatibilidad con la API de S3, permitiendo integrar el almacenamiento mediante herramientas y clientes compatibles con dicho protocolo.

La selección del proveedor no deberá introducir dependencias directas en los módulos funcionales.

### 3.11.2. Separación de responsabilidades

Los archivos binarios se almacenarán en Railway Storage Buckets.

PostgreSQL almacenará únicamente:

- Identificador del archivo.
- Tenant propietario.
- Nombre original.
- Clave o ruta del objeto en el bucket.
- Tipo MIME.
- Extensión.
- Tamaño.
- Fecha de carga.
- Usuario que realizó la carga.
- Referencia al recurso funcional relacionado.
- Estado y metadatos adicionales necesarios.

No se almacenará el contenido binario de los documentos directamente en PostgreSQL.

### 3.11.3. Organización de archivos

Los objetos se organizarán mediante separación lógica por empresa y tipo de documento.

Estructura conceptual:

```text
bucket/
└── tenants/
    ├── {tenantId-1}/
    │   ├── invoices/
    │   ├── manifests/
    │   ├── expenses/
    │   ├── payments/
    │   └── advances/
    │
    └── {tenantId-2}/
        ├── invoices/
        ├── manifests/
        └── expenses/
```

La estructura de directorios es una convención de organización y no constituye por sí sola un mecanismo de seguridad.

El aislamiento real deberá garantizarse mediante validaciones del backend y control de acceso a los objetos.

### 3.11.4. Flujo de carga

Se utilizará carga directa desde el frontend al almacenamiento mediante URLs firmadas temporales.

Flujo:

1. El frontend solicita autorización para cargar un archivo.
2. El backend valida identidad, membresía, tenant, permisos y condiciones del archivo.
3. El backend genera una URL firmada temporal para la carga.
4. El frontend utiliza esa URL para enviar el archivo directamente al bucket.
5. El sistema verifica que el objeto se haya cargado correctamente.
6. Se registran los metadatos y la referencia del archivo en PostgreSQL.

Este mecanismo evita que los archivos tengan que atravesar innecesariamente el backend.

### 3.11.5. Flujo de descarga

1. El usuario solicita acceder a un archivo.
2. El backend valida su identidad y autorización.
3. Comprueba la pertenencia del archivo al tenant correspondiente.
4. Genera una URL firmada temporal para descargarlo.
5. El frontend utiliza esa URL para obtener el archivo.

Los archivos serán privados. No se permitirá acceso público directo a documentos empresariales.

### 3.11.6. Seguridad y validaciones

La implementación deberá contemplar:

- Validación de tamaño máximo.
- Validación de extensión.
- Validación de tipo MIME.
- Nombres internos únicos o aleatorios.
- Autorización por tenant.
- URLs firmadas con expiración.
- Protección contra acceso directo no autorizado.
- Verificación de cargas completadas.
- Control de referencias huérfanas.
- Eliminación de objetos conforme a las reglas de conservación de información.

Las validaciones de tipo MIME y extensión no deberán considerarse suficientes por sí solas para garantizar que un archivo sea seguro.

### 3.11.7. Abstracción del proveedor

Se implementará una abstracción de almacenamiento independiente del proveedor.

El backend utilizará un contrato equivalente a:

```csharp
public interface IFileStorageService
{
    Task<UploadUrlResult> GenerateUploadUrlAsync(...);

    Task<DownloadUrlResult> GenerateDownloadUrlAsync(...);

    Task DeleteAsync(...);

    Task<bool> ExistsAsync(...);
}
```

La implementación inicial será:

`RailwayFileStorageService`

Los módulos funcionales utilizarán la abstracción y no dependerán directamente de los SDK o detalles particulares de Railway.

La arquitectura deberá permitir sustituir el proveedor por Cloudflare R2, AWS S3 u otro servicio compatible sin rediseñar los módulos funcionales.

## 3.12. Infraestructura y despliegue

### 3.12.1. Plataforma

Se utilizará Railway como plataforma inicial de despliegue.

Los componentes principales serán:

- Servicio backend ASP.NET Core.
- Servicio PostgreSQL.
- Servicio frontend independiente.
- Railway Storage Buckets para archivos.

### 3.12.2. Backend

El backend se desplegará como un único servicio ASP.NET Core.

Se utilizará Docker con un Dockerfile explícito.

Todos los módulos funcionales estarán incluidos en el mismo backend.

No se desplegará un servicio independiente por módulo.

### 3.12.3. Frontend

El frontend se desplegará independientemente del backend.

Su comunicación con el backend se realizará mediante la API REST.

### 3.12.4. Base de datos

PostgreSQL será administrado como servicio de infraestructura independiente.

El backend accederá a la base de datos mediante Entity Framework Core.

### 3.12.5. Migraciones

Las migraciones de EF Core se ejecutarán mediante un proceso controlado e independiente del arranque normal del backend.

No se ejecutarán automáticamente en cada inicio de instancia o réplica.

Se deberá garantizar que las migraciones se ejecuten de manera controlada antes de desplegar versiones que dependan de los cambios de esquema.

### 3.12.6. Escalabilidad

La arquitectura estará preparada para escalar horizontalmente mediante réplicas del mismo servicio backend cuando la demanda lo requiera.

El aumento de réplicas no implicará separar los módulos funcionales en servicios independientes.

La solución deberá considerar:

- Sesiones persistidas.
- Cachés coherentes o invalidables.
- Procesos idempotentes.
- Control de concurrencia.
- Acceso compartido a PostgreSQL.
- Almacenamiento externo de archivos.

No se incorporará Redis inicialmente.

## 3.13. Estrategia de pruebas

La estrategia de pruebas será progresiva.

Inicialmente se implementarán:

- Pruebas unitarias.
- Pruebas de integración.

Posteriormente podrán incorporarse:

- Pruebas de arquitectura.
- Pruebas end-to-end.
- Pruebas de carga y rendimiento.

La incorporación de mayor complejidad y exigencia en las pruebas se realizará conforme a las decisiones de evolución del proyecto.

No se establece inicialmente un porcentaje mínimo obligatorio de cobertura.

Se deberán priorizar pruebas para:

- Reglas financieras.
- Cálculos de liquidaciones.
- Rentabilidad.
- Aislamiento multi-tenant.
- Autorización.
- Sesiones.
- Integridad de datos.
- Concurrencia.

### 3.14.1. Tecnologías no incorporadas inicialmente

No se utilizarán inicialmente:

- Microservicios.
- RabbitMQ.
- Redis.
- Kubernetes.
- Bases de datos independientes por módulo.
- Bases de datos independientes por empresa.

- Almacenamiento persistente de archivos en el disco local del contenedor.
- Row-Level Security de PostgreSQL.

La incorporación futura de estas tecnologías requerirá una justificación técnica y una decisión explícita.

## 3.15. Criterios arquitectónicos de aceptación

La arquitectura se considerará correctamente implementada cuando:

1. El backend opere como una única aplicación modular.
2. Los módulos tengan límites y responsabilidades claramente definidos.
3. Las dependencias respeten Clean Architecture.
4. CQRS esté implementado mediante Commands, Queries y handlers.
5. Mediator de Martin Othamar sea el mecanismo de despacho seleccionado.
6. Los módulos se comuniquen mediante contratos públicos y eventos internos.
7. La persistencia utilice un único ApplicationDbContext.
8. El aislamiento multi-tenant se aplique mediante TenantId y validaciones de backend.
9. La API REST esté centralizada y versionada.
10. El frontend se encuentre separado del backend.
11. Los estados del servidor y del cliente utilicen las herramientas definidas.
12. Las sesiones puedan invalidarse desde el backend.
13. Los procesos de migración estén controlados.
14. Los motores especializados encapsulen cálculos y reglas reutilizables.
15. Los archivos se almacenen en Railway Storage Buckets.
16. PostgreSQL conserve metadatos y referencias, no el contenido binario.
17. Las cargas y descargas utilicen URLs firmadas temporales.
18. Los módulos funcionales no dependan directamente del proveedor de almacenamiento.
19. La solución permita sustituir el proveedor de archivos mediante su abstracción.
20. Las pruebas iniciales cubran reglas críticas, aislamiento y persistencia.
