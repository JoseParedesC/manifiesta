# 04. Requerimientos del producto (PRD)

## 4.1. Propósito de la sección

Esta sección establece los requerimientos generales del producto, describiendo las capacidades funcionales y condiciones no funcionales que debe satisfacer el sistema SaaS de gestión administrativa, operativa y financiera para empresas de transporte de carga.

Su propósito es servir como referencia para:

- Orientar el desarrollo del producto.
- Establecer las capacidades esperadas de cada módulo.
- Mantener coherencia entre el alcance funcional y la arquitectura.
- Proporcionar una base para la creación de épicas y User Stories.
- Facilitar la validación del producto frente a las necesidades del negocio.
- Mantener trazabilidad entre los requerimientos y las funcionalidades implementadas.

Esta sección tiene un enfoque de especificación general estilo PRD. No pretende describir cada interacción, pantalla, validación o comportamiento técnico individual.

El detalle funcional y los criterios de aceptación se desarrollarán posteriormente en las User Stories.

## 4.2. Objetivos del producto

El producto tiene como objetivo proporcionar una plataforma centralizada que permita a empresas de transporte de carga administrar sus operaciones y controlar su situación financiera mediante información organizada, relacionada y trazable.

### 4.2.1. Objetivos principales

1. Centralizar la información administrativa, operativa y financiera de cada empresa.
2. Facilitar el control de vehículos, conductores, clientes y proveedores.
3. Gestionar los servicios de transporte y sus manifiestos asociados.
4. Controlar ingresos, gastos, cuentas por cobrar, cuentas por pagar y anticipos.
5. Facilitar la liquidación mensual de vehículos y la liquidación de conductores.
6. Conocer la rentabilidad individual de cada vehículo.
7. Facilitar la distribución de utilidades de acuerdo con los acuerdos establecidos.
8. Proporcionar reportes para apoyar las decisiones administrativas y financieras.
9. Permitir que varias empresas utilicen la plataforma de manera independiente y segura.
10. Reducir la dependencia de hojas de cálculo y registros dispersos.

### 4.2.2. Resultados esperados

El sistema deberá permitir que una empresa pueda:

- Conocer los servicios de transporte realizados y su estado.
- Consultar los ingresos asociados a sus operaciones.
- Identificar los gastos generales y los gastos asociados a vehículos.
- Consultar saldos pendientes de clientes y obligaciones con proveedores.
- Identificar anticipos entregados y recibidos que requieren conciliación.
- Consultar la rentabilidad de cada vehículo.
- Consultar las liquidaciones de vehículos y conductores.
- Mantener trazabilidad sobre las operaciones y movimientos financieros.
- Obtener información consolidada de su operación.

## 4.3. Alcance general del producto

El producto estará orientado exclusivamente a empresas dedicadas al transporte de carga.

Se desarrollará como una plataforma SaaS multiempresa, donde cada organización administrará su propia información dentro de una infraestructura compartida.

### 4.3.1. Características generales

| Característica | Definición |
|---|---|
| Modelo de producto | Software as a Service (SaaS) |
| Tipo de cliente | Empresas de transporte de carga |
| Multiempresa | Sí |
| Moneda inicial | Pesos colombianos (COP) |
| Gestión de flota | Flota propia |
| Gestión operativa | Servicios de transporte y manifiestos |
| Gestión financiera | Finanzas operativas y administrativas |
| Facturación | Documentos internos de facturación |
| Liquidaciones | Vehículos y conductores |
| Reportes | Operativos, administrativos y financieros |
| Gestión documental | Adjuntos básicos |
| Acceso | Aplicación web |

### 4.3.2. Consideraciones de alcance

El producto estará orientado a administrar la operación y las finanzas internas de las empresas de transporte.

No pretende sustituir un sistema contable completo ni implementar automáticamente todas las obligaciones tributarias, laborales o regulatorias de la empresa.

Las funcionalidades relacionadas con procesos legales o integraciones externas deberán considerarse como capacidades independientes y no se asumirán como parte del alcance inicial.

## 4.5. Reglas de negocio generales

Las siguientes reglas establecen principios que deberán respetarse en los diferentes módulos del producto.

### 4.5.1. Multiempresa

- La información de cada empresa deberá permanecer aislada.
- Cada registro perteneciente a una empresa deberá estar asociado a su contexto de tenant.
- El contexto de empresa deberá determinarse en el backend mediante la identidad y membresía autenticadas.
- El frontend no será una fuente confiable para determinar a qué empresa pertenece una operación.
- Las relaciones entre registros deberán respetar el mismo contexto de empresa, salvo excepciones explícitamente autorizadas.

### 4.5.2. Gestión financiera

- Todos los valores monetarios se manejarán en pesos colombianos (COP).
- Los cálculos financieros utilizarán tipos numéricos adecuados para evitar errores de precisión.
- Los pagos y las aplicaciones de pagos a obligaciones deberán tratarse como operaciones diferenciadas.
- Los anticipos entregados a conductores no se reconocerán automáticamente como gastos.
- Los anticipos recibidos de clientes no se reconocerán automáticamente como ingresos si el ingreso ya fue reconocido mediante la operación correspondiente.
- Los préstamos otorgados se administrarán como cuentas por cobrar y no como gastos operativos.
- Los gastos deberán identificarse como generales o directamente asociados a vehículos, según corresponda.
- Los movimientos financieros deberán conservar su relación con los documentos y operaciones de origen.

### 4.5.3. Servicios y facturación

- Los servicios de transporte deberán mantener su identidad independientemente de las facturas que los documenten.
- Una factura podrá agrupar varios servicios.
- Un servicio podrá tener facturación parcial cuando las reglas comerciales lo permitan.
- La información económica no deberá duplicarse innecesariamente entre las facturas y los servicios relacionados.
- Los cambios posteriores de asignación de vehículo o conductor no deberán modificar la información histórica del servicio.

### 4.5.4. Liquidaciones y rentabilidad

- Las liquidaciones de vehículos se generarán por periodo mensual e independientemente para cada vehículo.
- Los resultados de periodos cerrados deberán conservarse como registros históricos.
- La rentabilidad deberá calcularse utilizando los movimientos financieros y operativos correspondientes.
- Un gasto no deberá contabilizarse dos veces al consolidar la rentabilidad.
- Las liquidaciones de conductores deberán mantenerse separadas de las liquidaciones de vehículos.
- La distribución de utilidades deberá respetar los acuerdos registrados y no asumir porcentajes universales.

### 4.5.5. Integridad y trazabilidad

- Las operaciones financieras relevantes deberán poder rastrearse hasta su origen.
- Los cierres y procesos de liquidación deberán protegerse frente a ejecuciones duplicadas o inconsistentes.
- Los registros históricos relevantes deberán conservar su integridad.
- Las modificaciones de información sensible deberán poder auditarse.

Estas reglas constituyen principios generales. Las condiciones específicas, excepciones y validaciones se detallarán en las User Stories correspondientes.

## 4.6. Requerimientos no funcionales

Los requerimientos no funcionales establecen las cualidades y condiciones generales que deberá cumplir el producto.

En esta versión se definen de forma cualitativa. Los objetivos cuantitativos y límites operativos se determinarán posteriormente en la sección de infraestructura y dimensionamiento.

### 4.6.1. Seguridad

- El sistema deberá proteger el acceso mediante autenticación y autorización.
- Las contraseñas locales deberán almacenarse utilizando mecanismos seguros de hashing.
- Las sesiones deberán poder revocarse.
- Los endpoints deberán validar la identidad, membresía, empresa activa y permisos correspondientes.
- Los archivos adjuntos deberán almacenarse de forma privada.
- Las operaciones sensibles deberán contar con controles de autorización.
- La comunicación entre cliente y servidor deberá utilizar HTTPS.

### 4.6.2. Aislamiento multiempresa

- El sistema deberá garantizar separación lógica de datos entre tenants.
- Las consultas deberán respetar automáticamente el contexto de empresa.
- Las operaciones de escritura deberán validar la pertenencia de las entidades al tenant correspondiente.
- No deberán permitirse relaciones entre registros de empresas diferentes sin una autorización y justificación explícitas.
- Deberán existir pruebas que permitan verificar la ausencia de acceso cruzado entre empresas.

### 4.6.3. Integridad y confiabilidad

- Las operaciones que involucren varios registros relacionados deberán mantener consistencia transaccional cuando corresponda.
- Los procesos financieros deberán protegerse frente a duplicaciones.
- Las operaciones críticas deberán manejar correctamente errores y reintentos.
- Los procesos de cierre deberán evitar resultados inconsistentes.
- La información histórica deberá conservarse de forma confiable.

### 4.6.4. Rendimiento

- La solución deberá diseñarse para ofrecer una experiencia de uso fluida.
- Las consultas deberán evitar operaciones innecesariamente costosas.
- Los procesos de cálculo deberán poder ejecutarse de forma independiente y ser susceptibles de optimización.
- La arquitectura deberá permitir mejorar el rendimiento sin modificar innecesariamente los módulos funcionales.

Los tiempos máximos de respuesta, volumen de solicitudes y concurrencia esperada se definirán en la sección de infraestructura y dimensionamiento.

### 4.6.5. Disponibilidad y continuidad

- El sistema deberá estar preparado para operar como servicio SaaS.
- Los mecanismos de persistencia deberán proteger la información ante fallos de aplicación.
- La solución deberá contemplar estrategias de respaldo y recuperación.
- Los procesos de despliegue y actualización deberán minimizar riesgos de pérdida o inconsistencia de datos.

Los objetivos de disponibilidad, recuperación y pérdida máxima de información aceptable se definirán posteriormente.

### 4.6.6. Mantenibilidad y modularidad

- La solución deberá mantener separación de responsabilidades entre módulos.
- Los módulos deberán exponer contratos claros para su interacción.
- La lógica de negocio deberá permanecer desacoplada de los mecanismos de transporte HTTP y presentación.
- Los componentes compartidos deberán evitar duplicación de código y reglas.
- Los motores especializados deberán encapsular cálculos y procesos reutilizables.
- Los cambios en un módulo deberán minimizar el impacto sobre los demás.
- La solución deberá facilitar la incorporación progresiva de nuevas funcionalidades.

### 4.6.7. Usabilidad

- La interfaz deberá facilitar la navegación entre módulos.
- La información deberá presentarse de forma clara y consistente.
- Los formularios deberán facilitar el registro y consulta de información.
- Los errores deberán comunicarse de forma comprensible.
- La interfaz deberá mantener patrones de interacción reutilizables.
- Las operaciones frecuentes deberán poder realizarse sin recorridos innecesariamente complejos.

### 4.6.8. Auditoría y trazabilidad

- El sistema deberá conservar información relevante sobre las operaciones críticas.
- Los cambios sensibles deberán permitir identificar el usuario responsable y el momento de ejecución.
- Los movimientos financieros deberán mantener relaciones con sus documentos y operaciones de origen.
- Los procesos de liquidación deberán conservar resultados históricos.
- Los mecanismos de auditoría deberán respetar el aislamiento multiempresa.

### 4.6.9. Escalabilidad y evolución

- La solución deberá permitir incrementar los recursos disponibles para el backend y la base de datos según las necesidades del producto.
- La arquitectura deberá permitir escalar horizontalmente el servicio backend cuando sea necesario.
- La incorporación de nuevas capacidades no deberá exigir una migración obligatoria hacia microservicios.
- La estructura deberá permitir evaluar futuras integraciones y servicios externos sin comprometer el núcleo funcional.

## 4.7. Restricciones y exclusiones del producto

## 4.8. Dependencias y consideraciones generales

### 4.8.1. Dependencias funcionales

El funcionamiento de algunas capacidades depende de la información administrada por otros módulos.

| Capacidad | Dependencias principales |
|---|---|
| Operaciones | Business Partners, Fleet e Identity & Tenants |
| Facturación | Operations y Business Partners |
| Finanzas | Billing, Operations y Business Partners |
| Liquidación de vehículos | Operations y Finance |
| Liquidación de conductores | Operations y Finance |
| Distribución de utilidades | Finance y Settlements |
| Reporting | Información de los módulos funcionales |

Estas dependencias representan relaciones funcionales. No implican que un módulo deba acceder directamente a las estructuras internas de otro.

### 4.8.2. Consideraciones técnicas

- La API central será responsable de recibir las solicitudes y coordinar los casos de uso.
- Los procesos de negocio podrán apoyarse en motores especializados reutilizables.
- Los cálculos complejos deberán mantenerse separados de los controladores y componentes de presentación.
- Los procesos deberán recibir solicitudes mediante contratos definidos y devolver resultados estructurados.
- El frontend deberá reutilizar componentes, servicios, hooks y utilidades compartidas.
- El backend deberá reutilizar reglas y servicios de dominio sin duplicar lógica entre módulos.
- La información persistirá en una base de datos PostgreSQL compartida.
- Los archivos se almacenarán en un servicio de almacenamiento de objetos compatible con S3.
- La solución se desplegará inicialmente en Railway.

Los detalles de configuración, recursos, costos, capacidad, proveedores y dimensionamiento se documentarán en la sección de infraestructura.

## 4.9. Criterios generales de aceptación del producto

El producto podrá considerarse funcionalmente conforme con esta especificación cuando:

1. Permita administrar de manera independiente varias empresas.
2. Mantenga aislamiento de información entre empresas.
3. Permita administrar usuarios, membresías y permisos.
4. Permita registrar clientes, proveedores y vehículos.
5. Permita gestionar servicios de transporte y sus manifiestos.
6. Permita emitir documentos internos de facturación y registrar facturas recibidas.
7. Permita controlar ingresos, gastos, pagos, cobros y saldos pendientes.
8. Permita gestionar anticipos y préstamos.
9. Permita generar liquidaciones mensuales por vehículo.
10. Permita consultar la rentabilidad individual de los vehículos.
11. Permita generar liquidaciones administrativas de conductores.
12. Permita gestionar acuerdos y distribuciones de utilidades.
13. Proporcione reportes operativos y financieros.
14. Mantenga trazabilidad de los procesos y movimientos relevantes.
15. Respete las restricciones funcionales y técnicas definidas para la primera versión.

La validación detallada de cada capacidad se realizará mediante los criterios de aceptación definidos en sus respectivas User Stories.

## 4.10. Trazabilidad entre PRD, épicas y User Stories

Se establece una estructura documental jerárquica para mantener relación entre las necesidades del producto y las funcionalidades desarrolladas.

### 4.10.1. Convención de identificadores

| Elemento | Formato | Ejemplo |
|---|---|---|
| Requerimiento PRD | `PRD-[MÓDULO]-###` | `PRD-FIN-001` |
| Épica | `EPIC-[MÓDULO]-###` | `EPIC-FIN-001` |
| User Story | `US-[MÓDULO]-###` | `US-FIN-001` |
| Criterio de aceptación | `AC-##` | `AC-01` |

Los identificadores serán únicos y estables. Una modificación en el contenido de un requerimiento no deberá provocar innecesariamente el cambio de su identificador.

### 4.10.2. Relación jerárquica

La trazabilidad seguirá esta estructura:

**Requerimiento PRD → Épica → User Story → Acceptance Criteria**

- Cada requerimiento PRD podrá estar relacionado con una o varias épicas.
- Cada épica deberá identificar los requerimientos que cubre.
- Cada User Story deberá pertenecer a una épica.
- Cada User Story deberá incluir sus criterios de aceptación.
- Los criterios de aceptación deberán permitir verificar el comportamiento esperado de la historia.

Una épica podrá cubrir varios requerimientos y un requerimiento transversal podrá relacionarse con épicas de diferentes módulos.

### 4.10.3. Responsabilidad documental

| Artefacto | Responsabilidad |
|---|---|
| SDD / PRD | Definir las necesidades y capacidades generales del producto. |
| Épicas | Organizar las grandes capacidades funcionales. |
| User Stories | Especificar comportamientos y necesidades concretas del usuario. |
| Acceptance Criteria | Definir condiciones verificables para aceptar cada historia. |
| Tareas técnicas | Describir el trabajo necesario para implementar las historias. |

### 4.10.4. Control de cambios

Los cambios de alcance deberán reflejarse en el PRD cuando modifiquen las capacidades generales del producto.

Los cambios exclusivamente relacionados con el comportamiento detallado de una funcionalidad podrán gestionarse en las User Stories correspondientes, siempre que no contradigan los requerimientos aprobados.

Cuando una decisión técnica afecte una capacidad funcional o una restricción del producto, deberá revisarse la trazabilidad y actualizarse la documentación correspondiente.
