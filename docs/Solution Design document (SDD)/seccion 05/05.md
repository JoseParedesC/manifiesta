# 05. Usuarios, membresías, roles y permisos

## 5.1. Objetivo

Definir el modelo de usuarios, pertenencia a empresas y autorización de acceso a las funcionalidades del sistema.

El modelo debe garantizar:

- Identidad global de usuarios dentro de la plataforma.
- Separación de usuarios y autorizaciones entre empresas.
- Configuración flexible de roles por empresa.
- Control de acceso basado en permisos.
- Protección de las capacidades administrativas de cada empresa.
- Aislamiento de información entre tenants.
- Trazabilidad de los cambios relacionados con usuarios y autorizaciones.

La autorización se implementará mediante RBAC (*Role-Based Access Control*), con roles personalizados por empresa y un catálogo centralizado de permisos administrado por el producto.

## 5.2. Modelo conceptual

El sistema manejará cuatro conceptos principales:

| Concepto | Descripción |
|---|---|
| Usuario | Identidad global de una persona dentro de la plataforma. |
| Membresía | Relación entre un usuario y una empresa. |
| Rol | Conjunto de permisos que una empresa configura y asigna a sus usuarios. |
| Permiso | Capacidad funcional predefinida por el producto que puede habilitarse en un rol. |

No se implementará un sistema independiente de perfiles de usuario.

La función que desempeñe una persona dentro de una empresa no determinará automáticamente sus permisos. El acceso dependerá exclusivamente de los roles asignados.

### 5.2.1. Usuario global

Un usuario tendrá una única identidad dentro de la plataforma, independientemente de la cantidad de empresas a las que pertenezca.

Características:

- Puede pertenecer a varias empresas.
- Puede tener diferentes roles en cada empresa.
- Sus roles y permisos son independientes por empresa.
- Puede cambiar el contexto de empresa activa sin utilizar cuentas diferentes.
- La autenticación identifica al usuario global; la autorización depende de su membresía y contexto empresarial.

La información de autenticación será independiente de las asignaciones de roles y permisos.

### 5.2.2. Membresía empresarial

La membresía representa la relación de un usuario con una empresa.

Cada membresía:

- Pertenece a un único usuario y una única empresa.
- Determina si el usuario está habilitado para participar en esa empresa.
- Permite asociar uno o varios roles.
- Tiene un ciclo de vida independiente de la identidad global.
- Consume un cupo de usuario de la empresa cuando está habilitada.

Un mismo usuario puede tener membresías independientes en diferentes empresas.

El backend deberá comprobar la membresía y su estado en cada solicitud que opere dentro del contexto de una empresa.

## 5.3. Modelo de autorización RBAC

### 5.3.1. Catálogo centralizado de permisos

El producto mantendrá un catálogo único de permisos predefinidos.

El catálogo será administrado exclusivamente por el producto y no podrá modificarse desde las empresas.

Las empresas no podrán:

- Crear permisos.
- Eliminar permisos.
- Modificar identificadores de permisos.
- Modificar su definición funcional.
- Crear permisos administrativos propios.

Cada empresa podrá configurar cuáles permisos del catálogo estarán habilitados para cada uno de sus roles personalizados.

La configuración de permisos de una empresa no afectará a las demás empresas.

### 5.3.2. Convención de permisos

Se utilizará la convención:

`Modulo.Recurso.Accion`

Ejemplos:

| Permiso | Descripción |
|---|---|
| `Fleet.Vehicles.View` | Consultar vehículos. |
| `Fleet.Vehicles.Create` | Registrar vehículos. |
| `Fleet.Vehicles.Edit` | Modificar vehículos. |
| `Fleet.Vehicles.Delete` | Solicitar eliminación o inactivación según las reglas del recurso. |
| `Operations.Services.View` | Consultar servicios de transporte. |
| `Operations.Services.Create` | Registrar servicios. |
| `Finance.Expenses.Create` | Registrar gastos. |
| `Finance.Payments.View` | Consultar pagos. |
| `Settlements.VehicleSettlements.Create` | Generar liquidaciones de vehículos. |

Los permisos estarán organizados por módulo, recurso y acción.

No se incluirán alcances sobre registros individuales dentro del identificador del permiso, como `All` o `Assigned`.

La autorización de un permiso no sustituye las validaciones de:

- Tenant al que pertenece el registro.
- Relaciones y propiedad de los datos.
- Estado de la operación.
- Integridad financiera
